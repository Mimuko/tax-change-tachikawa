以下の個人開発プロジェクトを進めてください。

# プロジェクト概要

仮称：
**「税金で、何が変わった？」**

立川市の一般市民向けに、公開されている行政データを分かりやすく再編集し、

- 自分の街で何が変わったのか
- 介護を必要とする人は増えたのか
- サービスの受け皿はどう変わったのか
- 支える人はどう変わったのか
- 行政支出や市民負担はどう変わったのか

を、数値の羅列ではなく視覚的に理解できるWebサービスを作ります。

MVPは以下に限定します。

- 対象自治体：立川市
- 対象テーマ：介護
- 対象期間：直近5年程度
- ホスティング：Netlify
- 対象ユーザー：立川市の一般市民

---

最低限、以下をMarkdownへ整理してください。

## requirements.md

### 背景

出発点となった疑問は、

「介護の需要がある一方で、介護職の賃金や供給体制はどう変化しているのか」

というものです。

調査していく中で、行政支出について、

「何に使われたか」だけではなく、
「その結果、社会がどう変わったのか」

が一般市民から見えにくいことを課題としています。

---

## コンセプト

**「税金はどこへ行った？」ではなく「税金で、何が変わった？」**

ただしUX上の入口は「税金」ではなく、

**「自分の街はどう変わった？」**

としてください。

行政や政策を評価するサイトではありません。

公開データを再編集し、

**ユーザー自身が変化に気づき、考えられる状態を作る**

ことが目的です。

---

# UX原則

最重要方針：

**「読ませる」より「理解・知ってもらう」**

第一階層では具体的数値を大量表示せず、

- 変化
- 差
- 関係性

を視覚的に伝えてください。

情報階層は以下を基本とします。

```text
何が変わった？
↓
どの程度変わった？
↓
なぜそう見える？
↓
内訳は？
↓
具体的な値は？
↓
その根拠は？
```

具体値・定義・原典は第二階層以降に置いてください。

---

# 表現ルール

サイト側から以下のような価値判断は行わないでください。

NG例：

- 「介護政策は悪化している」
- 「税金が有効活用されている」
- 「介護職の賃金は低すぎる」
- 「この政策は失敗している」

代わりに、

- 増減
- 変化率
- 需要と供給の変化差
- 目標値と実績値の差

など、観測できる事実を表示してください。

因果関係は断定しません。

---

# MVP非対象

以下はMVPでは実装しません。

- 全国自治体比較
- 将来予測
- 因果推論
- 個人の納税額試算

ただし、

**自治体が過去に設定した計画値と実績値の比較**

は将来予測ではないため、取得可能なら実装候補とします。

---

# MVPで確認したい主な変化

トップレベルでは以下のような意味単位で表示してください。

## 1. 介護を必要とする人

候補指標：

- 65歳以上人口
- 第1号被保険者数
- 要支援・要介護認定者数
- 認定率

## 2. サービスの受け皿

候補指標：

- 施設数
- 事業所数
- 定員
- サービス利用者数

サービスは内部では行政上の正式分類を保持してください。

UI上は必要に応じて、

- 住む
- 通う
- 自宅で受ける
- 地域密着・複合

など、市民向けカテゴリへ再分類してください。

内部分類と表示分類は分離してください。

## 3. 介護を支える人

候補指標：

- 介護職員数
- 可能なら常勤換算職員数

## 4. 支える人の待遇

候補指標：

- 介護職賃金
- 東京都全職種平均との比較
- 実質賃金

立川市単位の賃金データが取得できない場合は、

**「東京都の参考指標」**

として明確に区別してください。

## 5. 行政支出・市民負担

候補指標：

- 介護保険給付額
- サービス別給付額
- 介護保険事業歳出
- 介護保険料基準額
- 一般会計からの繰入等

---

# 指標定義ルール

現時点の基本方針：

- 利用者数：実人数
- 職員数：実人数
- 施設数：居住型介護施設として行政上分類されているもの
- 事業所数：居宅系サービスを提供する事業所

ただし、行政データ上の正式定義を優先してください。

実装時に独自解釈で統合しないでください。

行政の正式分類を内部データとして保持し、
UI用カテゴリは別レイヤーで定義してください。

---

# 比較ルール

以下を表示可能にしてください。

- 前年比
- 5年前比

必要に応じて以下で正規化してください。

- 人口
- 高齢者人口
- 高齢化率

単純な件数だけでは比較しないようにしてください。

---

# 変化表現

「増加」「減少」「横ばい」の閾値を恣意的に決めないでください。

初期実装では、

- ↑
- →
- ↓
- 変化率

など、方向と量を中心に表示してください。

評価語を使用する場合は、必ず判定基準を仕様として明文化してください。

---

# データ鮮度・更新

- 原則、自治体や公的機関のデータ更新後に最新情報を取得
- 古いデータには「最終更新：YYYY年」等を表示
- 更新失敗時のエラーは一般ユーザー画面には表示しない
- 管理者向けログまたは監視で検知可能にする

---

# データ欠損

データが存在しない、取得できない、比較不能の場合は推測して補完しないでください。

表示可能な情報のみ表示します。

データ取得できない場合は、

「この項目について、現在参照できる行政データを確認できませんでした」

など、根拠データが存在しない・取得できていないことを明確にしてください。

「0」として扱わないでください。

---

# 出典・証跡

各数値について、最低限以下を保持してください。

- 出典名
- 対象年度
- 取得日
- 原典URL
- 指標定義
- 単位
- 元データの値
- 加工後の値
- 加工方法

元データからどのように変換したか追跡可能にしてください。

可能であればデータ取得時の原文・CSV・JSON等も保存し、再検証できる構成にしてください。

---

# 利用上のスタンス

本サービスは行政データそのものを作成・管理するものではありません。

以下に近い注意書きを掲載してください。

「本サイトは公開されている行政データを独自に収集・整理・可視化するものです。原典の数値・定義等に関するお問い合わせは、各データの掲載元へお願いいたします。」

---

# アクセシビリティ

インクルーシブデザインを採用してください。

最低限：

- 色だけで増減を表現しない
- グラフにテキスト代替を持たせる
- キーボード操作可能
- スマートフォン対応
- 十分なコントラスト
- スクリーンリーダーで意味が伝わる構造
- prefers-reduced-motion に配慮

---

# Error / Empty State

以下を明確に区別してください。

- データなし
- 比較不可
- 定義変更あり
- データ取得失敗
- 原典側で未公開

ユーザー画面では技術的エラーコードを直接表示しないでください。

---

# 非機能要件

- モバイル優先
- 高速表示
- 各主要ブラウザ最新版対応
- 旧ブラウザは対象外
- Netlifyへデプロイ
- 更新失敗監視
- SEO基本対応
- OGP対応
- SNS共有対応
- Lighthouseを意識した実装

---

# 成功条件

以下をAcceptance Criteriaとしてください。

1. 初見ユーザーが30秒以内に、立川市の介護について「何が増えた・減った・停滞しているか」を3点以上説明できる
2. 閲覧後、自分が気になる点・疑問・自治体に確認したいことを1つ以上言語化できる
3. 気づいた内容をSNS等で共有できる
4. 具体的な数値を覚えていなくても、立川市の介護がこの数年間でどう変化したか説明できる

# UI / デザイン方針

行政ダッシュボードによくある、

- KPIカード大量配置
- 円グラフ大量配置
- 表中心

にはしないでください。

**Data Storytelling / Scrollytelling**

を意識してください。

技術候補：

- Next.js
- TypeScript
- Tailwind CSS
- shadcn/ui
- Observable Plot
- Recharts

シンプルなUIグラフではRechartsを併用して構いません。

# 技術構成

MVPでは過剰設計を避けてください。

第一候補：

```text
公的オープンデータ
↓
取得スクリプト
↓
parse / normalize
↓
JSON
↓
Next.js
↓
Netlify
```

MVPでは必ずしもDBを使用する必要はありません。

将来データ量が増えた場合、

- Supabase
- Neon
- PostgreSQL

等へ移行可能なデータ構造にしてください。

以下の順で進めてください。

## Phase 1 要件正本化

上記内容をMarkdownへ整理してください。

- MVP外

`architecture.md` に以下を整理してください。

- エラー監視
- 将来DB移行方針

```text
自分の街はどう変わった？
↓
介護を必要とする人
↓
サービスの受け皿
↓
支える人
↓
待遇
↓
行政支出
```

要件MDを正本として実装してください。

# 最終的な実装原則

**コードより先に要件を更新すること。**

プロジェクト内のMarkdownを仕様の正本とし、
実装と仕様が乖離しないようにしてください。

また、過度な抽象化・過剰な汎用化はMVPでは避け、
まず

**立川市 × 介護 × 直近5年**

を高品質に成立させることを最優先としてください。
